# Workflow

## Evidence First

Before writing, inspect in this order:

1. Repo `README.md`
2. Product docs or demo script
3. Live URL
4. Demo/video URL
5. Package manifests or architecture docs
6. Relevant prior posts from Max

If a claim is not grounded in repo, docs, or demo evidence, do not use it.

## Output Format

Default output:

- 5 primary drafts
- 1 short punchy draft
- 1 technical-insider draft

For each draft include:

- angle label
- post text
- recommended URL
- one-line why-it-works note

## Draft Mix

Target weighting:

- 60% product outcome
- 30% technical depth
- 10% contrarian tension

Every draft should satisfy both:

- understandable by non-engineers in under 5 seconds
- rewarding to technical readers with at least one real signal

## Angle Library

Pick across these:

1. Outcome-first
2. Builder insight
3. Contrarian truth
4. Technical proof
5. Demo-led workflow compression

## Structure Patterns

Pattern A:

1. Sharp claim or pain
2. What the product does in plain English
3. One technical proof point
4. Demo or repo URL

Pattern B:

1. Old slow workflow
2. New compressed workflow
3. Why it works
4. Demo URL

Pattern C:

1. What most people miss
2. What Max built
3. Specific stack or infra detail
4. Open loop or question

## Best Signal Sources

Prefer these proof points:

- hard engineering constraint
- evaluation depth
- infrastructure choice
- deterministic behavior
- deployment reality
- live demo
- public repo

Prefer one concrete proof point over three vague ones.
